# Протокол разметки эталона

Эталон отвечает на вопрос: выполнен ли критерий в этой работе на этом
коммите. По нему считаются ложные «закрыто», ложные «не закрыт» и
покрытие. Сами сдачи и метки лежат вне репозитория, в `data/raw/`.

## Что размечаем

Единица разметки: один вердикт, то есть сдача на коммите и критерий, у
личных работ ещё и человек. Выборка случайная, с разбивкой по командам,
работам и типам проверки. Разбиение на части идёт по командам: вердикты
одной команды не независимы.

Типы `command` и `http` здесь не размечаем: стенд на старом коммите уже
не поднять.

## Метки

| Метка | Когда ставим |
|---|---|
| закрыт | в работе есть то, что требует критерий, и нет признаков из `bad` |
| не закрыт | артефакта нет, он пустой, совпадает с `bad` или не выполнено требование из текста критерия |
| не уверен | решить нельзя и по файлам, и по фактам GitHub |

К метке записываем места в работе, на которых она держится, и уверенность
от 0 до 1. Цитаты должны дословно совпадать с файлом.

Дополнительные отметки:

- `criterion_defect`: критерий спрашивает то, чего к этой работе ещё нет.
  Метку ставим по смыслу работы, а случай считаем отдельно;
- `judge_reason_wrong`: вердикт судьи верный, но обоснование приписывает
  работе то, чего в ней нет.

## Правила чтения критерия

1. **Текст критерия берём из снимка**, который получил судья. Если текст
   потом поменялся, размечаем по снимку и пишем об этом в заметке.
2. **Слова «каждый», «все», «целиком» читаем буквально.** Один вывод без
   ссылки при критерии «каждый вывод подкреплён ссылкой» значит «не закрыт».
3. **Перечень в `good` это примеры**, если сам критерий не требует всего
   списка. Отказ опирается на фразу из текста, `good` или `bad`.
4. **Артефакт ищем по смыслу**, а не по имени файла.
5. **Работа команды шире ветки роли.** Роли работают в своих ветках, поэтому
   смотрим и открытые на момент проверки PR других ролей. Если артефакта
   нет нигде, он отсутствует, даже когда отвечает за него другая роль.
6. **Формально заполненное считается.** Слабое обоснование или ошибка в
   расчёте не делают критерий невыполненным, пока не совпадают с `bad`.
   Такие находки записываем в заметку.
7. **Опубликованный текст важнее сайта курса.** Если они разошлись, верен
   текст на потоке, а расхождение передаём автору курса.
8. **Для типа `structure` решает `schema`.** Если текст критерия обещает
   больше, чем `schema`, метку ставим по `schema`, а расхождение записываем
   в заметку и передаём автору курса.

## Чьи работы можно размечать моделью

Работы отдаём внешней модели только с согласия их авторов на оценку с
участием модели. Сейчас оно есть у 4 курса и у практики 3 курса, в том
числе для закрытых репозиториев практики. Без такого согласия работу
размечает только человек.

## Что видит разметчик

| Данные | Откуда |
|---|---|
| Задание и снимок критерия | платформа |
| Работа на коммите, с историей git | репозиторий команды |
| Изменённые файлы, описание и обсуждение PR | GitHub |
| Проверки CI на коммите и обязательные проверки ветки | GitHub |
| Открытые на момент проверки PR других ролей и основная ветка | GitHub |

Разметчик **не видит** вердикт и обоснование судьи, прошлые вердикты, отчёт
судьи в PR, итоги приёмки и расшифровки. Отчёт судьи убирается из пакета
автоматически. Открытые PR других ролей судья сейчас не получает: это
намеренное отличие разметчика, эталон должен отражать работу команды.

Обсуждение PR берём только до момента проверки: позже участники
пересказывают вердикт. Описание PR и настройки ветки GitHub отдаёт на
сегодня, а не на дату проверки. Если настройка могла поменяться, в заметке это указываем.

## Порядок разметки

1. Модель размечает вслепую.
2. Модель другого семейства размечает вслепую ещё раз.
3. Автор курса смотрит все расхождения с судьёй и между моделями, а также
   случайную выборку совпавших, особенно где все сказали «закрыт».
4. Считаем согласие модели и человека. Модель не считается эталоном:
   итоговые метки ставит человек, а числа и интервалы поправляются по его
   выборке (prediction-powered inference).

Отметки и решения приёмки меткой не считаются: решение ставится за работу,
а не за критерий, а вопрос по критерию может остаться без отметки.

## Как хранятся метки

`data/raw/etalon/labels.jsonl`, одна строка на вердикт: `verdict_id`,
`repo`, `sha`, `criterion_key`, `label`, `rater`, `blind`,
`criterion_defect`, `judge_reason_wrong`, `note`. Метки, поставленные не
вслепую, помечаются `blind: false`.

Пакет для разметчика собирает `scripts/build_packet.py`.
